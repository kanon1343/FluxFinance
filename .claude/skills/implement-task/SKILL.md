# タスク実装ワークフロー

対象タスク: $ARGUMENTS（未指定なら `tasks.md` で最初の未完了 `[ ]` タスク）

## 1. 把握する（必要な箇所だけ読む）

- `.kiro/specs/flux-finance/tasks.md` で対象タスクと、そこに書かれた要件番号を確認する。
- `requirements.md` と `design.md` は、Grep で該当する要件番号やセクションを探し、その部分だけを読む。全文は読まない。
- 変更対象のファイルが分かっていればそれを直接読む。分からなければ Explore サブエージェントに場所を探させる。
- 複数ファイルにまたがる変更や設計判断を伴うタスクなら、実装前に方針を3〜5行でユーザーに示す。plan モードで動いている場合は計画として提示する。

## 2. 実装する

- CLAUDE.md の「絶対に守るルール」に従う。規約に迷ったら `nextjs-guidelines` skill の該当セクションを読む。
- ロジックを追加・変更したら、同じ階層の `*.test.ts(x)` にテストも追加・更新する。
- 編集のたびに Biome hook が走る。エラーが返ってきたらすぐに直す。

## 3. 検証する

- `test-runner` サブエージェントで typecheck・lint・test を実行する。
- 失敗があれば直して、再実行する。同じ失敗が3回続いたら手を止めてユーザーに報告する。

## 4. レビューする

- `code-reviewer` サブエージェントに変更ファイルを渡す。
- ⚠️ や ❌ なら「改善必須」を直し、検証からやり直す（最大3回）。上限を超えたら設計の見直しが必要だとユーザーに報告する。

## 5. 完了させる

- `tasks.md` の該当タスクを `[x]` にする。
- 変更内容・レビュー点数・検証結果を短く報告する。
- コミットはユーザーに頼まれた時だけ行う。形式は CLAUDE.md の「コミット形式」に従い、本文にレビュー点数を入れる。
- 最後に「次のタスクに進む前に `/clear` するとコストを抑えられます」と一言添える。
